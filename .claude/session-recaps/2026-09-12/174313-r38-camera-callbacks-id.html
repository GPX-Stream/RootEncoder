R38 — Camera Callbacks Carry a Camera Id

Extended CameraCallbacks so onCameraOpened, onCameraDisconnected, and onCameraError all carry the camera id the callback is actually about, closing the gap R23/R37 left open at the interface boundary. Build and test green; PR #8 open for review.

What happened

›
Root cause found

CameraCallbacks' three race-relevant methods carried no camera id. A consumer could only ask getCurrentCameraId() after the fact — and that field has no generation gate on its own assignment, unlike the callback dispatch R23/R37 already protect.

Fix built and verified

Interface now takes cameraId: String on the three methods. Every call site inside Camera2ApiManager.kt passes the id captured in that attempt's own closure. Camera1ApiManager.java passes its int index as a string.

Judgment call

Design fork, resolved

›

Camera1 vs Camera2 id types

The task brief flagged "a consumer whose semantics make a camera-id parameter awkward" as an escalate-don't-guess case. Camera1ApiManager (int index, synchronous, no race) matched that description. Resolved without escalating: Java can't consume a Kotlin default-parameter interface method, so the real choice was one shared String signature vs. two divergent interfaces. Went with one signature — Camera1ApiManager passes String.valueOf(cameraSelect), which is a low-risk, ordinary conversion since Camera1 has no race to protect against anyway. Called out in the canonical block in case this needs revisiting.
